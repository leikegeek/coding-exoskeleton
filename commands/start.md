# /start — 流水线 A 入口：从需求开始

当用户输入 `/start` 时，启动流水线 A（需求 → 技术方案）。

## 触发方式

- `/start SV-34577` — 带需求编号
- `/start SV-34577 需求文档内容...` — 带需求编号和文档
- `/start 给订单列表加一个按供应商筛选的功能` — 口头需求（SV-ID 可选，建议提供）

## 执行流程

### 预检步骤（自动执行，对用户透明）

检查当前项目是否已生成项目画像文件：

1. 检查项目根目录下是否存在 `AGENTS.md` 文件
2. **如果已存在**：读取 `AGENTS.md`，将其中的技术栈、架构模式、模块结构等信息作为项目上下文，进入第一步
3. **如果不存在**：暂停当前流程，引导用户完成项目初始化
   - 告知用户：「检测到当前项目尚未初始化项目画像，需要先完成初始化以确保 AI 准确理解项目上下文。正在启动 /init 流程...」
   - 执行 `/init` 命令的完整流程（读取 `init.md`）
   - 完成后告知用户：「项目画像已就绪，继续执行 /start 流程...」
   - 读取刚生成的 `AGENTS.md`，然后继续第一步

> **关于 Hooks**：Hooks 治理环境由 `install.ps1` 在安装插件时统一写入 `~/.cursor/hooks.json`（全局用户级），无需每个项目单独安装。

### 第一步：需求录入

1. 从 `AGENTS.md` 的 `需求编号正则` 字段读取匹配规则（默认 `SV-\d+`），检查用户输入中是否包含需求编号
2. **有需求编号**：解析需求文档，提取编号、标题、描述、验收标准
3. **无需求编号**：提炼需求要素，然后提示用户（非阻塞，用户可跳过）：

> 建议提供需求编号以保证全链路可追溯（技术方案 → 分支 → 变更清单 → 技术参考文档）。如果这是一个小改动且暂无编号，可以跳过，后续产出物将以时间戳或简短标识命名。

   - 用户提供编号时：正常使用
   - 用户确认跳过时：任务契约中 `需求编号` 字段填「无（轻量需求）」，文档命名使用 `{日期}-{简短标识}-tech-design.md`

4. 读取项目上下文：优先使用 `AGENTS.md` 中的项目画像（技术栈、架构模式、模块结构），仅在画像信息不足时补充扫描构建文件
5. 建立任务契约，进入**设计模式**：
   - 模式：设计模式
   - 需求编号：推荐项（强烈建议提供），无编号时以用户确认的简短标识替代
   - 允许写入路径：仅文档目录
   - 禁止项：不修改项目代码、不执行构建命令
6. **复杂度判定**：需求完整性门禁通过后，根据以下条件判定需求复杂度，向用户展示判定结果并确认（用户可覆盖）：

   **轻量需求（满足全部）**：
   - 影响模块数 <= 1
   - 无跨系统/跨服务调用变更
   - 无新技术组件引入
   - 无数据模型重构
   - 无接口破坏性变更

   **标准需求（满足任一）**：
   - 影响模块数 >= 2
   - 涉及跨系统/跨服务调用
   - 引入新技术组件
   - 数据模型重构
   - 接口破坏性变更
   - 用户明确要求完整方案

   判定结果决定 A2 走哪条路径（标准路径 or 轻量路径），用户可覆盖（如将轻量升级为标准）。

### 第二步：技术方案设计与评审

根据第一步复杂度判定的结果，分别执行标准路径或轻量路径。读取并执行 `tech-design` skill：

#### 标准路径（复杂度判定 = 标准需求）

1. 澄清阻断问题（3-5 个/轮，优先选择题）
2. 阅读项目代码，识别受影响的模块和层级
3. **数据规模澄清**：基于代码阅读结果，列出核心表的当前/预期数据量，等待用户确认。数据规模将作为方案中分页、索引、批处理策略的硬约束
4. 提出 2-3 种方案，附取舍分析和推荐
5. 输出结构化技术方案文档
   - 若方案涉及 HTTP 接口新增/修改或 MQ 契约变更（techStack 属于后端 profile 时），第三部分「数据与接口改动」必须引用 `backend-api-contract` skill 输出接口契约子节，覆盖请求/响应/错误/幂等/兼容性
6. 委派 `design-reviewer` 子代理执行独立评审（独立上下文，不携带方案生成过程的思考链）
7. 若方案涉及新增模块、引入新技术组件、跨模块数据流变更或数据模型重构，委派 `architect` agent 执行架构决策审查

#### 轻量路径（复杂度判定 = 轻量需求）

1. 快速澄清（1-2 个问题，仅阻断性缺口）
2. 阅读相关代码
3. 单方案直出（跳过多方案对比）
4. 输出精简方案文档（4 段结构）
5. 委派 `design-reviewer` 子代理执行独立评审
6. architect 子代理不触发

#### 第二步收口（标准/轻量路径共用）

上述产出全部完成后，本步允许写入的内容仅限技术方案/评审/架构审查**文档**（在约定文档目录下）。**禁止**在本步结束时：对项目**业务代码**做任何编辑、执行构建/测试、创建分支、启动 `/code` 或 B1 任务拆解、调用编码子代理。评审若给出「可开发」类结论，**只供第三步展示**，**不**作为开始编码的许可。

> **注意**：第二步到此为止。完成评审（和架构审查）后，**必须进入第三步的用户确认门禁**，不得跳过。尤其**不得**在「评审刚结束」的同一轮对话里，以「建议开发」「下一步实现」为理由自动进入编码。

### 第三步：用户确认技术方案（硬门禁 — 必须阻塞等待）

> **⚠️ 这是一个硬门禁：你必须在此处停止生成，等待用户的明确回复。在收到用户确认之前，禁止执行任何后续动作（包括第四步、任务拆解、创建分支等）。**

向用户展示以下内容后，**停止生成，等待用户回复**：

1. **技术方案摘要**：用 3-5 句话概括方案的核心设计（包括主要影响模块、核心数据流、关键设计决策）
2. **评审结论**：列出 design-reviewer 子代理发现的 Critical / Important / Nice-to-have 问题（如有架构审查结果也一并展示）
3. **结构化确认请求**：以明确分隔的选项形式展示，每个选项附简短说明：

> 以上是技术方案摘要和评审结论。请选择：
> - **确认通过** — 方案无问题，继续流程
> - **需要修改** — 请指出需调整的部分
> - **有疑问需澄清** — 请提出疑问

展示后必须结束本轮输出，等待用户明确选择。

**用户回复的处理规则**：
- 用户选择 **确认通过**：进入第四步
- 用户选择 **需要修改**：根据反馈修订技术方案文档，重新执行评审，然后再次进入本门禁等待确认（循环直到用户确认通过）。返回时根据当初的复杂度判定回到对应路径（标准/轻量）
- 用户选择 **有疑问需澄清**：逐一解答疑问，解答完毕后再次请求确认（循环直到用户确认通过）
- 用户回复了其他内容：判断意图，若无法判断则明确询问用户是否确认方案

### 第四步：出口选择

方案经用户确认后，读取 `context-compaction` skill，评估是否需要执行上下文压缩（尤其是选择「继续编码」时，A→B 衔接是关键压缩点）。

然后询问：

> 技术方案已确认。请选择：
> - **继续编码** — 直接进入编码阶段（流水线 B）
> - **断开** — 仅保存技术方案文档，后续通过 `/code SV-ID` 继续

**方案完整性检查项**（继续编码和断开均需执行）：
- 技术方案文件已落盘，文件名和正文均包含需求编号（无编号时以简短标识替代）
- 默认功能技术方案已包含 4 个核心部分：功能概述与边界、核心业务流程、代码实施位置、测试与验收
- 已包含核心业务流程图（mermaid）和关键异常流程
- 已包含代码实施位置，说明新增/修改代码的目录层次、模块、文件位置和参考实现
- 只有用户明确要求架构设计方案时，才要求完整 8 部分架构模板

**选择"继续编码"**：
- 完整性检查通过后，切换到编码模式，自动进入流水线 B
- 任一项缺失时，不得进入 B1；应回到第二步补齐方案并重新经过第三步用户确认

**选择"断开"**：
1. 执行方案完整性检查（同上检查项）
2. **若通过**：保存文档到 `docs/design/SV-xxxxx-tech-design.md`（如目录不存在则自动创建），标记为正式版，结束当前流程
3. **若未通过**：向用户提示缺失项并给出选择：
   > 方案缺少以下内容：{缺失项列表}。
   > 断开后续接编码时可能遇到问题。请选择：
   > - **补齐后断开** — 回到方案补充缺失内容
   > - **标记为 draft 断开** — 保存为 `SV-xxxxx-tech-design-draft.md`，续接时需先补齐

## 关键约束

- 设计模式下，Hooks 会拦截构建/提交类命令
- 技术方案文档中必须包含需求编号（或用户确认的简短标识）
- 断开后，技术方案文档是续接流水线 B 的唯一依据
